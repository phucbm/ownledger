# 001: ownledger v1, from planning to the owner's own ledger live

Written: 2026-11-21. Status: In progress

## Goal

Replace a personal finance app (the owner's: MISA Sổ Thu Chi) with a ledger the owner runs through AI chat. v1 is done when:

1. `ownledger` is published on npm (with provenance) and anyone can `init` and `deploy` their own.
2. The owner's full history from MISA is imported into the owner's private data repo with nothing lost, every wallet's balance matching MISA's.
3. The owner adds transactions, asks reports and sees the dashboard through their own connector in Claude (and ChatGPT if it works, see Phase 0).

## Architecture

```
User's GitHub                         User's Cloudflare
┌─────────────────────────┐           ┌──────────────────────────────────────┐
│ my-money (private)      │◀─ GitHub ─│ Worker "my-money" (code = ownledger) │◀── Claude / ChatGPT  (/mcp, OAuth)
│  data/  imports/        │   App     │  /mcp   MCP, Streamable HTTP         │◀── Browser (/ dashboard, PWA later)
│  package.json → ownledger│  token   │  /api   JSON for the dashboard       │
│  wrangler.jsonc         │           │  /oauth GitHub sign-in, owner only   │
│  .github/workflows      │──deploy──▶│  KV: OAuth grants, parsed-ledger cache│
└─────────────────────────┘           └──────────────────────────────────────┘
```

- The Worker is stateless about finances: GitHub is the only store. KV holds OAuth grants and a cache of the parsed ledger keyed by commit SHA (safe to wipe).
- Reads: fetch the repo's data at `main` (one archive or tree request, not one call per file; to measure in Phase 2), parse, cache by SHA. All reports are computed in the Worker; the AI client only receives small answers.
- Writes: build the change, run the full check on the resulting data in the Worker, then commit through the GitHub API (one commit, atomic, with the expected parent SHA so a concurrent change is refused). The repo's Action runs `ownledger check` as a second guard.
- Network: GitHub's API only (plus price sources a user explicitly enables later). Stated in the README and easy to audit.

## The user's data repo (what `init` creates)

```
my-money/
├─ data/
│  ├─ meta.yaml          format version, base currency, locale, owner's GitHub login
│  ├─ accounts.yaml      every account: id, name, type, asset, opened, closed?, details{}
│  ├─ assets.yaml        VND (base), USD, GOLD_CHI, fund and ticker symbols…
│  ├─ categories.yaml    income and spending tree (default from init, in vi or en)
│  ├─ plans.yaml         instalments, loans, insurance premiums, deposits' schedules
│  ├─ budgets.yaml       optional
│  ├─ prices.csv         date,asset,price (in base currency)
│  └─ ledger/yyyy/mm.jsonl   one transaction per line
├─ imports/
│  ├─ raw/               original exports, kept as received
│  └─ <source>.mapping.yaml   one per source app, written by the AI on first import
├─ AGENTS.md             schema + rules for any AI (copied from the package, refreshed on update)
├─ package.json          "ownledger": "^x.y.z"
├─ wrangler.jsonc        main: node_modules/ownledger/worker.js, assets from the package
└─ .github/workflows/    check.yml (every push), deploy.yml (on main, optional)
```

### Transactions

One JSON object per line, lines balance in base currency:

```json
{"id":"t_8f3a…","date":"2026-11-18","time":"18:40","note":"Lunch","tags":[],"who":null,"event":null,
 "lines":[{"account":"card-sacom","amount":-168500},{"category":"food/eating-out","amount":168500}],
 "src":{"import":"misa","key":"…"}}
```

- A line has either `account` or `category`; `amount` is signed, in base currency; the lines of a transaction sum to 0.
- Non-base assets add `asset` and `qty`: buying 2 chỉ of gold is `{"account":"cash","amount":-17200000}` + `{"account":"gold","asset":"GOLD_CHI","qty":2,"amount":17200000}`. Same shape for funds, stocks, ETFs, foreign currency.
- Transfers, card payments, deposits opened or closed, loans given or repaid: lines between accounts only, no category, so they are never counted as income or spending.
- `who` and `event` stay as fields (MISA's "Chi cho ai" and "Chuyến đi/Sự kiện"), plus free `tags`.
- `src` ties an imported transaction to its source row (stable key, see Import). Transactions added in chat have no `src`.
- `void: true` instead of deleting (history stays readable); a real delete only through git.

### Accounts and types: how nothing breaks

- `type` is one of a registry the package ships (`cash`, `bank`, `ewallet`, `credit_card`, `bnpl`, `deposit`, `savings_goal`, `gold`, `fund`, `stock`, `etf`, `crypto`, `insurance`, `loan_given`, `loan_taken`, `other`). Each type has an optional schema for `details` (credit card: statement day, due day, limit; deposit: principal, rate, term, start, maturity, rollover; savings goal: target, by).
- **A type the engine doesn't know is accepted as a plain account** (balance only) with a warning, never an error. Extra unknown keys in `details` are kept and passed through.
- Assets are rows in `assets.yaml`; adding an ETF is adding a row and a price.
- `meta.yaml` holds `format: N`. A package version that needs a newer format refuses with "run `npx ownledger migrate`"; migrations are code in the package, rewrite the files in one reviewable commit, and are tested on fixtures of every older format.
- Package semver: patch and minor never need a migration; a format change is a major.

### Plans (instalments and schedules)

`plans.yaml`: `{id, kind: instalment | bnpl | loan_taken | loan_given | insurance_premium | deposit, account, principal?, count?, every: month | quarter | year, start, amount?, fee?, rate?, note}`. The engine produces each plan's due dates; a payment transaction names its plan (`"plan":"p_…"` on the transaction); "what's due" and "what's left" are computed, never written.

## Import (generic; MISA first)

1. `npx ownledger import <file>` (in an AI coding tool, which reads `AGENTS.md`): the CLI profiles the file (sheets, headers, sample rows, distinct values per column, totals it can see) and prints it for the AI.
2. The AI writes `imports/<source>.mapping.yaml`: how to read rows, column → field, wallet → account (with type and details), source category → ownledger category, how transfers are marked and paired, how to read the source's own balances for the reconcile. The owner approves it (the category map especially).
3. The importer (plain code) runs the mapping:
   - **Raw kept**: the file copied to `imports/raw/`.
   - **Stable key per source row**: hash of (source account, date, time, amounts, category, note, occurrence index among identical rows).
   - **Transfers paired** into one transaction; anything unpaired is listed, never dropped.
   - **Reconcile**: per source account, closing balance and totals in/out must equal the source's figures, and every source row must be accounted for (imported, paired, or listed with a reason). Otherwise the import refuses and shows the difference.
   - Amounts rounded to whole đồng (exports carry float noise like `.3200002` and `-0`); the rounding is reported.
4. **Re-import** of a newer export with the same mapping: new rows added, known keys skipped, rows changed or gone in the source reported for the owner to decide. Running twice changes nothing.
5. Later imports from the same app also from the dashboard (file read in the browser, the mapping applied by the Worker, preview, commit).

### MISA Sổ Thu Chi export, as observed (the first preset)

- One xlsx; sheet 1 and each other sheet is one wallet (sheet names truncated by Excel to 31 characters and de-duplicated with `_NN` suffixes, so the full wallet name is not always in the sheet name).
- Rows 1 to 9: title, period, totals (Tổng thu, Tổng chi, Số dư đầu kì, Số dư cuối kì); row 10 headers: STT, Ngày (dd/mm/yyyy), Giờ, Số tiền thu, Số tiền chi, Số dư, Hạng mục cha, Hạng mục con, Chi cho ai, Chuyến đi/Sự kiện, Diễn giải. Newest first.
- Transfers have no category; the note says `Chuyển từ <wallet>` / `Chuyển tới <wallet>`, and each transfer appears once in each wallet's sheet. Deposits opened and closed: `Gửi tiết kiệm tài khoản <name> (Chuyển từ X)`, `Tất toán sổ tiết kiệm <name> (Chuyển tới X)`; interest adjustments on closing appear as separate rows.
- Some income rows have no category either (only a note); the mapping must catch them (not every uncategorised row is a transfer).
- Users encode facts in wallet names (e.g. statement and due day of a card as emoji + number); the AI should lift those into `details` with the owner's confirmation.
- Small negative balances on closed deposit wallets are MISA rounding; the reconcile must match them exactly anyway and report them.
- Lost in the export, to be entered once: wallet types, card limits, deposit rates and terms (when not in the name), attachments, budgets, recurring items.

## MCP tools (v1)

Read: `about` (version, format, data repo, last commit), `rules` (what the AI must follow: preview first, never invent amounts, categories list), `accounts` (with balances, by type), `transactions` (search by date range, account, category, text, amount; paginated), `report` (period: month | year | custom; by category, account, who, event, tag; vs previous period), `net_worth` (now and monthly series), `cards` (owed, statement, due date, what to pay), `plans_due` (instalments and premiums due in the next N days, what's left per plan), `deposits` (maturing next, interest), `today` (one short block: due soon, maturing, budget over, anything odd).

Write (always `preview` → owner's go → `apply` with the preview's fingerprint; apply refuses if `main` moved): add/edit/void transaction, add/edit/close account, add plan, add price, add/edit category (with remap of existing lines). Each apply is one commit with a readable message.

Answers are short and computed; never raw dumps of thousands of rows.

## Dashboard (v1)

Served by the user's own Worker, same GitHub sign-in, light only. Pages: Overview (this month, net worth, due soon), Transactions (filter, search), Accounts (by type; card, deposit, investment detail), Plans (instalments, schedule), Reports (month/year by category, trends), Import (upload, mapping preview, reconcile view). Read-only except Import (writes through the same preview → commit). PWA manifest later; keep it installable-friendly from the start (no server-rendered state, all from `/api`).

## CLI

`init` (asks: folder/repo name, base currency, category language, an export to import now?; creates the repo above; `gh repo create --private --push` when gh is logged in), `import`, `check`, `migrate`, `deploy`, `dev` (wrangler dev against the local `data/`, a fake sign-in, for development).

### `deploy`

1. Cloudflare sign-in (wrangler login in the browser).
2. Worker name (default = repo name) → `<name>.<subdomain>.workers.dev`; custom domain optional.
3. GitHub App through the manifest flow (CLI runs a localhost callback): one click creates the app in the user's account (permissions: Contents read/write on selected repos, nothing else), one click installs it on this repo only. The app's ID, private key, client ID and secret go to Worker secrets (never the repo, never printed).
4. Sign-in allowlist = the user's GitHub login (detected; more logins optional).
5. "Redeploy on every push?" (default yes): Cloudflare API token as a GitHub Actions secret via `gh secret set`, `deploy.yml` enabled.
6. Creates the KV namespace, deploys, prints the connector URL (`/mcp`) and the dashboard URL, with one line on adding it in Claude and ChatGPT.

## Security and releases

- OAuth via Cloudflare's `workers-oauth-provider`; the Worker is the authorization server, GitHub only proves identity; the GitHub user token is not kept beyond sign-in; tokens given to Claude/ChatGPT are the Worker's own, revocable from the dashboard, expiring.
- Repo access with the GitHub App's installation token (short-lived, one repo).
- Published only from GitHub Actions with `npm publish --provenance`; 2FA on npm; few dependencies; a CHANGELOG entry per release; majors never auto-merged (Dependabot config in the user repo allows auto-merge for patch/minor only after `check` passes).
- Dashboard: strict CSP, no third-party scripts or fonts from CDNs.
- Tests on made-up fixtures only. **The owner's real data never enters this public repo.**

## Phase 0 findings (2026-11-22)

- **ChatGPT:** accepts custom remote MCP (streaming HTTP, OAuth, write tools). Plans are unclear: OpenAI's help article says writes are Business/Enterprise/Edu only, the dev docs say Plus/Pro too. Developer mode is not required in the current help article. OAuth must issue refresh tokens (`offline_access` in scopes) and support DCR or CIMD. Not tested in v1 (decision 17); the README states what is known.
- **Claude:** DCR + PKCE + RFC 8414/9728 metadata. Callback is `https://claude.ai/api/mcp/auth_callback` (allow `claude.com` too). `@cloudflare/workers-oauth-provider` 1.2.4 covers this (KV `OAUTH_KV`). MCP via `agents`' `createMcpHandler`: stateless, **no Durable Objects**. `McpAgent` is deprecated.
- **Deploy to Cloudflare button:** the template must be public. Not verified whether the user's copy can be private. GitHub App creation can't run inside the button flow. **v1: `deploy` CLI only**; the README says so.
- **GitHub App manifest:** POST manifest to `github.com/settings/apps/new`, then `code`, then `POST /app-manifests/{code}/conversions` returns id, slug, pem, client_id/secret. `hook_attributes.active:false` is allowed. Up to 10 `callback_urls`. Install via `github.com/apps/<slug>/installations/new`. One app for both sign-in (user-to-server OAuth) and repo access (installation token) is standard. Localhost redirect still to be confirmed live in Phase 5.
- **Wrangler from node_modules:** **verified** (dry-run deploy and `wrangler dev`). `main: node_modules/ownledger/dist/worker.js` bundles its relative imports; `assets.directory` inside node_modules is served, with `run_worker_first` for `/api/*`, `/mcp`, `/oauth/*`.
- **npm:** `ownledger` is free. Trusted publishing is configured on the package's settings page, so the package must exist first (0.0.1 published locally, decision 14). Provenance is automatic for a public repo. Needs npm ≥ 11.5.1, Node ≥ 22.14. A new trusted-publisher config expires after 2 days with no publish.

## Proposed category tree (default for `init`; the owner's MISA map is decided in Phase 3)
